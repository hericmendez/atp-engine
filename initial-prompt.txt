# ATP Engine — Initial Agent Prompt

Você está trabalhando no desenvolvimento da **ATP Engine (Ash Twin Project Engine)**.

Antes de escrever qualquer código, você deve compreender e respeitar integralmente a documentação existente no repositório.

## 1. Primeira regra: não programe imediatamente

Sua primeira tarefa é **reconhecer o projeto**, não implementar funcionalidades.

Leia obrigatoriamente:

```text
AGENTS.md
engineering-rules.md
docs/stack.md
docs/classification.md
docs/identity-resolution.md
docs/sources.md
docs/persistence.md
docs/ai.md
docs/api.md
docs/roadmap.md
```

Se algum desses arquivos não existir, **não invente seu conteúdo**.

Verifique quais documentos realmente existem no repositório e informe quais estão ausentes.

Depois, inspecione:

```text
package.json
tsconfig.json
docker-compose.yml
.env.example
src/
tests/
```

ou os equivalentes existentes.

---

# 2. Não assuma que o repositório está vazio

Antes de criar ou modificar arquivos:

1. examine a estrutura atual;
2. identifique código existente;
3. identifique configurações existentes;
4. identifique dependências já instaladas;
5. identifique testes existentes;
6. identifique decisões arquiteturais já implementadas;
7. verifique o estado do Git.

Não sobrescreva código existente sem entender sua finalidade.

Se houver implementação parcialmente pronta, **evolua-a em vez de recriá-la**.

---

# 3. Fonte de verdade

A hierarquia de decisão é:

```text
AGENTS.md
    ↓
```

---

# 4. Stack obrigatória

A stack oficial é:

```text
Runtime          Node.js
Language         TypeScript
API              Express
Validation       Zod
Database         MongoDB
Database Access  Mongoose ou MongoDB Driver
HTTP             native fetch / undici
Tests            Vitest
Lint             ESLint
Formatting       Prettier
Containers       Docker
Local AI         Ollama
Remote AI        Provider Adapter
Architecture     Modular / Clean-ish Architecture
```

Não substitua essas tecnologias por preferência pessoal.

Não introduza:

```text
Fastify
NestJS
Prisma
PostgreSQL
Jest
Axios
```

ou equivalentes como substitutos sem uma decisão arquitetural explícita.

---

# 5. Arquitetura obrigatória

O projeto deve preservar separação entre:

```text
Interfaces
    ↓
Application
    ↓
Domain

Infrastructure
    ↓
implements contracts
```

O domínio não pode depender diretamente de:

```text
Express
MongoDB
Mongoose
Ollama
HTTP clients
environment variables
```

Frameworks e ferramentas pertencem às bordas da aplicação.

---

# 6. ATP não é apenas um scraper

Não trate a ATP como um scraper tradicional.

O objetivo é construir uma:

> **Canonical Game Knowledge Engine**

O fluxo conceitual é:

```text
External Sources
       ↓
Discovery
       ↓
Normalization
       ↓
Classification
       ↓
Identity Resolution
       ↓
Canonical Catalog
       ↓
Enrichment
       ↓
AI-assisted Intelligence
```

A engine deve determinar:

* o que é um jogo;
* o que não é um jogo;
* quando dois resultados representam o mesmo jogo;
* quando dois resultados representam jogos diferentes;
* quando existe uma relação entre jogos;
* quais dados podem ser considerados canônicos;
* quais dados precisam de confirmação.

---

# 7. AI não é obrigatória

Esta é uma regra arquitetural fundamental.

A ATP deve funcionar sem qualquer LLM.

O fluxo preferencial é:

```text
Native Logic
     ↓
Confident?
 ├── YES → result
 └── NO
       ↓
      AI
       ↓
Valid?
 ├── YES → assisted result
 └── NO
       ↓
Native fallback
```

Nunca transforme uma dependência opcional em dependência obrigatória.

Se:

```text
Ollama
```

estiver indisponível, a engine deve continuar funcionando.

Se um provider remoto falhar, a engine deve continuar funcionando quando houver lógica nativa suficiente.

---

# 8. AI Provider

Nunca acople o domínio diretamente ao Ollama.

A arquitetura deve permitir:

```text
AIProvider
├── OllamaProvider
├── RemoteProvider
└── FutureProvider
```

AI deve produzir **propostas**, não alterar diretamente o banco.

Fluxo:

```text
AI
 ↓
Proposal
 ↓
Validation
 ↓
Application
 ↓
Domain rules
 ↓
Persistence
```

Nunca:

```text
AI
 ↓
MongoDB
```

---

# 9. Database-first

Quando a ATP precisar recuperar dados de um jogo individual:

```text
Database
   ↓
data complete?
 ├── YES → return
 └── NO
       ↓
External Sources
       ↓
Normalize
       ↓
Classify
       ↓
Resolve Identity
       ↓
Enrich
       ↓
Persist
       ↓
Return
```

Não consulte a web desnecessariamente.

Não crie duplicatas quando o jogo já existir no catálogo.

---

# 10. External Sources

As primeiras fontes são:

```text
Wikipedia
SteamDB
```

Mas elas devem ser implementadas como adapters independentes.

Nunca espalhe lógica específica da Wikipedia ou SteamDB pelo domínio.

Preferir:

```text
SourceAdapter
```

com implementações específicas.

A arquitetura deve permitir adicionar novas fontes posteriormente sem reescrever o pipeline.

---

# 11. Classification

A engine precisa distinguir jogos de outras mídias e entidades.

Exemplos:

```text
GAME
DLC
EXPANSION
MOVIE
TV_SHOW
ANIME
SOUNDTRACK
BOOK
HARDWARE
PROMOTIONAL
CHARACTER
FRANCHISE
PERSON
EVENT
UNKNOWN
```

A classificação nativa deve existir antes da classificação por IA.

Resultados ambíguos devem permanecer ambíguos.

Nunca invente certeza.

---

# 12. Identity Resolution

Identity resolution é uma das partes mais importantes da ATP.

O sistema precisa distinguir corretamente:

```text
Resident Evil 4 (2005)
≠
Resident Evil 4 (2023)
```

mas reconhecer:

```text
The Legend of Zelda:
Breath of the Wild — Wii U
=
The Legend of Zelda:
Breath of the Wild — Switch
```

Também deve ser capaz de representar relações complexas:

```text
Final Fantasy Tactics
        ↕
The War of the Lions
```

sem obrigatoriamente considerar os dois como entidades idênticas.

Regiões diferentes, como:

```text
NTSC-USA
PAL-EUR
```

não devem criar duplicatas quando representam o mesmo jogo.

---

# 13. Uncertainty

A ATP deve preferir:

```text
UNRESOLVED
```

a uma associação incorreta.

Um falso merge é potencialmente mais prejudicial do que manter dois candidatos separados até obter evidência suficiente.

Não use IA para transformar incerteza em uma resposta arbitrária.

---

# 14. Persistence

Somente dados validados podem entrar no catálogo canônico.

External source data:

```text
Source Data
    ↓
Normalization
    ↓
Classification
    ↓
Identity Resolution
    ↓
Domain Validation
    ↓
Canonical Game
    ↓
Persistence
```

Não persista diretamente o payload bruto de uma fonte como se fosse um Game canônico.

Quando necessário, preserve:

* source;
* external ID;
* provenance;
* evidence;
* timestamps.

---

Toda regra importante deve ser testável sem depender de:

```text

```

Priorize testes determinísticos para:

```text

classification
identity resolution
deduplication

```

Use mocks/stubs para integrações externas.

# 18. Regra contra overengineering

Não crie abstrações apenas porque a arquitetura permite.

Uma interface deve existir porque há uma necessidade real de desacoplamento.

Evite:

```text
factory
factory factory
generic repository
generic service
generic manager
generic helper
```

sem necessidade concreta.

Prefira código simples e explícito.

---

# 19. Regra contra código especulativo

Não implemente funcionalidades futuras "para deixar preparado".

Não crie:

* endpoints não previstos;
* providers não utilizados;
* adapters vazios;
* abstrações sem consumidor;
* tabelas/modelos especulativos;
* configurações que não possuem uso real.

Implemente apenas o necessário para a etapa atual.

---

# 20. Regra de mudanças

Cada alteração deve ter propósito claro.

Antes de modificar um arquivo, entenda:

```text
quem depende dele
quem ele depende
qual contrato ele implementa
```

Evite mudanças abrangentes quando uma alteração localizada resolve o problema.

---

# 21. Regra de dependências

Antes de adicionar uma biblioteca:

1. verifique se Node.js já oferece a capacidade;
2. verifique se alguma dependência existente resolve;
3. determine se a biblioteca realmente reduz complexidade;
4. avalie impacto na arquitetura.

Não adicione dependências por conveniência momentânea.

---

# 22. Git

```text

checkout -- .
```

nem descarte alterações existentes sem autorização explícita.

Não reescreva histórico.

Não faça commits automaticamente, a menos que isso seja solicitado.
